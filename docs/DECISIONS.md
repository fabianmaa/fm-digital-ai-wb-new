# Decisions log

Every decision taken under ambiguity during the redesign, with the alternative that was
discarded and the reason. Language architecture is not listed as an open decision: English
default + Spanish through the constants file is fixed by the brief (§2.4).

| # | Decision | Discarded alternative | Why |
| --- | --- | --- | --- |
| D-01 | Spanish lives at `/es/...` routes rendered by the same components. | Language stored only in React state/localStorage; separate Spanish build; `es.` subdomain. | Crawlable, shareable URLs with correct `lang`, canonical and hreflang; no duplicated page tree; no extra deployment. |
| D-02 | The Spanish URLs keep the English slugs (`/es/ai-agents`). | Translated Spanish slugs (`/es/agentes-ia`). | Avoids a large redirect map and route-mapping bugs; Spanish titles/meta are fully translated, which is what search snippets show. |
| D-03 | Spanish uses **tú**, neutral US Spanish, no regionalisms. | Formal *usted*; word-for-word translation. | The tone is a close local partner, and US Hispanic SMB marketing commonly uses *tú*; regional slang would date the site and exclude part of the audience. |
| D-04 | One dictionary object with nested EN/ES leaf pairs (`src/constants/copy.ts`), typed so components get the right language automatically. | Flat `key → {en, es}` map or a third-party i18n library. | TypeScript catches missing strings at build time; the copy document can be generated from the same tree; no runtime key errors, no extra dependency. |
| D-05 | English is always the default; the site does not auto-detect the browser language. | Redirect visitors by `navigator.language` or IP. | Auto-redirects surprise users, break shared links and can hurt SEO; the visible switch is enough. |
| D-06 | Exactly one primary action everywhere: **Get my free audit** → `/contact` (or the home form). | Secondary "Book a call" / "WhatsApp us" buttons competing with the audit. | The brief requires a single primary CTA; extra actions dilute the next step, especially for an owner who is skimming. |
| D-07 | Removed every inherited statistic (40% efficiency, 3x growth, 85% conversions, etc.). | Keeping them with a disclaimer or "typical results" footnote. | None could be substantiated; the brief forbids carrying them over, and an owner who has been burned by agency numbers notices them immediately. |
| D-08 | No testimonials, star ratings or client logos. Replaced with a studio note and qualitative project descriptions. | Inventing plausible testimonials or reusing unattributed quotes. | Fabricated proof is the fastest way to lose trust (and creates legal risk). Real quotes can be added later in the copy file. |
| D-09 | Aula Pro and Expert Path are described qualitatively: context, what we did, what changed. No percentages. | Publishing the old "85% of content in Google Top 1" and similar claims. | The projects are real and named on the old site, but the metrics were not verifiable. The work still shows judgment without invented outcomes. |
| D-10 | Removed the old "we will contact you within 24 hours" promise. | Keeping it as a conversion booster. | The brief explicitly flags it as unconfirmed; the new copy makes no time commitment until the owner decides on one. |
| D-11 | Removed the footer newsletter field. | Keeping it as a visual element with no backend. | A field that does nothing is a broken promise; there is no list, consent flow or backend. |
| D-12 | Removed Facebook and X icons; LinkedIn was kept initially and then **removed entirely** on 7 Nov 2026 (D-42). | Keeping all three icons with `#` links. | Two had no real destination; dead icons read as an unfinished site, and the owner later made the form the only contact channel. |
| D-13 | Contact happens **only through the audit form**. No phone, email, street address or social profile is published. | Publishing personal contact details found in the repository's CV PDF, or a secondary LinkedIn link. | Those are personal details, not verified business channels; the owner confirmed the form is the only contact route (7 Nov 2026). |
| D-14 | Removed the acronyms "SEO", "AI agents", "workflow automation" from customer-facing copy, replacing them with "be found on Google", "answer every customer", "follow up automatically". | A glossary that explains the technical terms. | The brief bans jargon and a glossary still asks the owner to learn a vocabulary; the URLs stay technical for continuity, the copy does not. |
| D-15 | Kept all nine existing routes and added `/contact`, `/privacy`, `/terms`, `/sitemap`. | Collapsing services into one page or dropping `/our-process` and `/case-studies`. | URL continuity (§4 technical rules); the extra pages are complete, not stubs. The internal `/insights` blog was later removed because the blog already exists as a separate WordPress installation. |
| D-16 | The home audit section keeps `id="contact"`, so old `/#contact` links still land on the form. | Relying only on the new `/contact` page. | Preserves every existing inbound anchor and link. |
| D-17 | Light, warm palette (paper / evergreen / terracotta) with one dark section and a dark footer. | Keeping the dark neon look, or an all-white corporate look. | The old direction read as a software product; all-white reads as a template. The warm light system matches clinics, restaurants and local trust signals. |
| D-18 | Fraunces (display) + Manrope (body), self-hosted. | Inter/Space Grotesk (generic), or a single sans throughout. | Fraunces gives the brand a voice without hurting legibility; Manrope is excellent at form and mobile sizes. Self-hosting avoids third-party requests. |
| D-19 | Provisional logo: an arch (open door) with a clay doorknob, plus a Fraunces wordmark. | A literal "AI" mark, a spark/robot, or using the old neon logo. | The door is local, human and legible at favicon size; the old logo belongs to the discarded visual world. Marked provisional for the owner's review. |
| D-20 | Photography from Burst (free commercial licence), self-hosted and resized to WebP at 800/1600 px. | Unsplash hot-linking, AI-generated people, or reusing the old dark product screenshots. | Real people at work, no licence ambiguity, no third-party runtime requests; the old screenshots are dark/technical and fight the new direction. |
| D-21 | The founder portrait was used in the first build and **removed** on 7 Nov 2026 when the owner moved to a corporate tone. | A stock portrait presented as the founder. | The portrait was the only verified real photograph, but the new direction removes the founder persona entirely; the corporate sections now use team-at-work photography. |
| D-22 | Runtime assets moved to `static/` and Vite's `publicDir` points there; the old `public/` folder was removed. | Keeping `public/` and adding new assets beside the old ones. | The old folder contained the neon logos, dead images and two personal PDFs. A clean asset root is easier to audit and deploy. |
| D-23 | Deleted the 14 legacy components, the old footer and the old pages that were replaced. | Leaving them in place, unused. | Dead code with hardcoded copy is exactly what the arbiter (and future maintainers) would trip over; the new tree has one component per responsibility. |
| D-24 | The contact endpoint and payload live in `src/lib/contactApi.ts`; components never build the request. | Inline `fetch` inside the form, as before. | One place to verify the contract, one place to test; the request shape is unchanged. |
| D-25 | Form requires only name + email, matching the API; phone, website and message stay optional. | Making phone required "because it converts better". | Extra required fields reduce completion and the API does not need them; the brief says preserve the contract. |
| D-26 | Form success copy makes no time promise; error copy offers a retry. | "We will contact you within 24 hours." | Same reason as D-10; the error path still gives the visitor a way forward without a secondary channel. |
| D-27 | The honey­pot stays client-side (`website1`), unchecked visually and never sent; local end-to-end testing is replaced by a mocked request plus a documented CORS test. | Removing the honeypot, or temporarily changing the API to allow localhost. | The API must not be modified; the honeypot is cheap protection; the brief's CORS procedure is followed and evidenced. |
| D-28 | Page titles, descriptions, canonical and hreflang are set on route change by `PageMeta`; `sitemap.xml` and `robots.txt` are static. | Adding SSR/prerendering or a meta-framework. | The site is already an SPA on static hosting; adding SSR is a platform change outside the brief. Static sitemap/robots keep crawlers covered. |
| D-29 | No analytics, advertising cookies or tracking pixels, so no cookie banner. | Installing GA4/Meta Pixel "because a marketing site should measure". | No consent flow exists and the privacy policy promises no tracking cookies; analytics can be added later with a proper consent decision. |
| D-30 | Pricing copy says a written fixed price is agreed after the free audit; no prices or ranges are published. | Inventing packages ("from $X/month"). | No verified pricing exists; invented numbers would be a promise the business has not made. |
| D-31 | Timeline copy is qualitative ("a small setup can be live in days; search work is measured in months") with no guaranteed dates. | Promising "results in 30 days". | Honest expectation-setting is part of the positioning; guaranteed dates would be unsubstantiated. |
| D-32 | No "no long-term contracts" claim. The process is staged so the client decides at each stage. | Promising no contracts. | That is a commercial policy the owner has not confirmed; the staged process communicates the same reassurance without a promise. |
| D-33 | The 404 page is a real, useful page with the audit CTA. | A bare "not found" line. | Every page carries the primary action; a lost visitor is still a potential client. |
| D-34 | Mobile menu is a full-screen forest panel with Esc, focus to close, scroll lock and `aria-expanded`. | A small dropdown under the header. | Large tap targets, clear hierarchy and proper keyboard behaviour on the device most owners use. |
| D-35 | `npm run dev` is pinned to port **5173** with `strictPort`. | Letting Vite choose the next free port. | The README and the owner's review loop depend on an exact URL; failing loudly is better than a silent port change. |
| D-36 | No Git operations, no commits, no remotes, no deployment. | Initialising the repository or pushing for convenience. | Explicitly reserved to the owner; this folder is the working copy he will commit. |
| D-37 | Known limitation: because of the SPA rewrite, unknown routes return `index.html` with HTTP 200 and render the 404 page client-side. | Server-side 404 handling. | The current hosting is a static Apache/cPanel rewrite; a real 404 status would need hosting-level rules, which can be added at deployment if desired. |
| D-38 | The audit is described as **30 minutes** in CTA microcopy and the contact page. | Removing any duration ("a short call"). | **Approved by the owner on 7 Nov 2026, wording unchanged.** |

## Standing rules — the `10k-websites` skill (owner-approved, 7 Nov 2026)

The `10k-websites` skill was installed under `.agents/skills/` as a **technique reference only**.
The only part of it used in this project is the scroll-hero pattern from its
`references/scrub-pipeline.md`, adapted to the frozen palette, typography, copy and the
React/Tailwind build with the current swappable media (no video scrub, no image sequences).

Permanently out of scope, and never to be run here:

- its setup wizard and the **Higgsfield** image/video connector;
- the **ffmpeg** asset pipeline;
- the **Hostinger** deploy connector;
- its one-page **plain-HTML/no-build** architecture;
- its copy gates and clickable question flow.

In any conflict between the skill and the project brief or the owner's instructions, the
brief and the owner's instructions win.

**Skills inventory.** `.agents/skills/` contains four folders: `frontend-design`,
`marketing-ideas` and `seo-geo` (all shipped with the original repository) and `10k-websites`
(the only skill installed during this project). No other skill was installed. No additional
skill may be installed without first reporting it to the owner; unused skills must not be
loaded into the project files.
